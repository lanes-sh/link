# ADR-008: A provider is a manifest, not a package

**Status:** accepted · **Milestone:** M2

## Decision

A provider declares *how to reach a vendor*, not *what the vendor can do*. Integration is expressed
as a **connectivity type** plus auth configuration, and capabilities are **discovered** rather than
declared.

Three connector kinds:

| Kind | For | Capabilities come from |
|---|---|---|
| `mcp` | a vendor with an official MCP server | `tools/list` on that server |
| `http` | a REST API described by OpenAPI | the spec, one capability per operation |
| `local` | our own code — `example`, and the owner layer's memory, skills, vault | written by hand |

The manifest schema is the same whether it arrives as a typed module in `providers/builtin` or as
YAML in `<workspace>/providers/*.yaml`. That is the point: a service we have never heard of is a
file, not a pull request.

## Why

`providers/gmail` reached **612 lines** for one read-only integration. `packages/policy` — the
enforcement layer that is the entire product — is 161. We were writing four times more code per
vendor than the thing that justifies the project, and four more providers meant ~2,400 lines of
vendor-specific maintenance nobody would keep current.

The four built-in providers now cost about 110 lines *in total*, and most of that is prose
explaining Google.

## Capabilities are discovered, never declared

For `mcp` and `http` the vendor is the source of truth. A declared capability list would go stale
the moment they shipped, and a stale list fails in the worst direction: an agent is told a tool
exists, calls it, and gets an error from a layer that cannot explain itself.

Discovery is cached in the database per provider, so a cold instance serves without a round trip,
and `lanes link doctor` reports capabilities that appeared upstream since you connected.

## The bundle split needs no curation

For `http`, the **HTTP method decides**: `GET`/`HEAD` are `read`, mutating verbs are `write`. A spec
therefore yields meaningful groups with no per-vendor judgement. For `mcp`, the upstream
`readOnlyHint` decides where present, and the tool name where it is not — an unrecognised verb
means `write`, which is the safer default.

## The one place per-vendor code is still allowed

`AuthStrategy`, and auth only. Real APIs do things no config language should try to express: bunq
generates an RSA keypair, runs a three-step handshake, signs every request, and verifies the
response signature. That earns roughly 150 lines. It must never come to mean per-endpoint code
again, which is why the seam is named for auth and takes a request rather than an operation.

## Consequences

**Vendor names leak into capability ids.** Notion names every tool `notion-*` and Google's
operationIds are dotted (`users.drafts.send`), so a redundant provider prefix is stripped at
discovery and the policy grammar accepts dots. The upstream name is kept in `target` and is what is
actually called — shortening changes how a capability is *addressed*, never which one runs.

**We inherit vendor schema problems.** Gmail's `MessagePart` contains `MessagePart[]`, which sends
an inlining OpenAPI tool generator into unbounded recursion; Linear puts `$defs` beside `properties`
and `$ref`s into them, so rebuilding a schema from `properties` alone leaves references that cannot
resolve. Both are handled where they arise rather than by hand-writing the affected tools.

**A spec is a security surface.** It decides which paths are called with the operator's token, and
`connect` grants everything a provider discovers — so the Google specs are **vendored and committed**
rather than fetched at connect time, and regenerated by `bun run vendor:google`. A spec
fetched from a third party could otherwise introduce a `DELETE` landing on the vendor's own host
holding a real credential.

**Redaction defaults to withholding every argument value** for proxied capabilities, because we did
not author them and cannot know what is sensitive. A manifest may opt specific keys back in.

**Nothing about the product thesis changes.** Default-deny, per-capability enforcement, audit with
redaction, and control-plane exclusion all survive untouched — and become *more* valuable, because
upstream MCP servers ship with no policy layer of their own.

## Rejected: a package per provider

The shape M1 shipped. It scales linearly in code with vendors, and the code is the least interesting
part of any of them — HTTP calls and response mapping that the vendor has already written down in a
spec or exposed through their own MCP server.

## Rejected: fetching OpenAPI specs at connect time

Convenient, and it keeps specs current automatically. It also means a third party chooses which
paths this process will call with a live mailbox token. Vendoring costs a script and a periodic
refresh; the alternative costs a supply-chain dependency on every provider.

---

**Amended by [ADR-010](010-non-http-connectors.md).** Two more kinds — `imap` and
`dav` — were added for iCloud, which publishes no MCP server and no REST API. The
test they had to pass, and the one any future kind must, is *protocol code, not
vendor code*: a kind that would name a vendor is the wrong shape.
